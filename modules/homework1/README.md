# Домашнее задание №1 — «ВышКат»

Консольное приложение учёта транспорта и вещей на балансе. Реализованы приёмка
транспорта через техосмотр, отчёты, подбор транспорта для новичков и инвентаризация.
Данные хранятся в памяти и теряются при завершении процесса. База данных,
веб-сервер, учёт поездок и сотрудников в объём этого задания не входят.

## Запуск

Нужны JDK 17 для модуля и JDK, совместимый с корневым Gradle 9.2 (например, 17 или 21).
Gradle Wrapper уже находится в репозитории. При первом запуске нужен доступ
к репозиториям зависимостей. Команды выполняются **из корня репозитория**:

```bash
# Интерактивное меню
./gradlew :modules:homework1:run --console=plain

# Воспроизводимая демонстрация без ручного ввода
./gradlew :modules:homework1:run --args='--demo' --console=plain

# Сборка, тесты, Checkstyle и минимальное покрытие строк 60%
./gradlew :modules:homework1:build
```

В Windows вместо `./gradlew` используйте `gradlew.bat`.
В IntelliJ IDEA обновите Gradle-проект после изменения `settings.gradle.kts`.
Можно запустить класс `ru.hse.vyshkat.Main` напрямую с JDK 17;
для демонстрации укажите аргумент `--demo`.

Модуль независим от практик: приведённые команды не запускают их тесты и серверы.
Сборка также создаёт архивы приложения в `build/distributions/`.
После распаковки ZIP приложение запускается скриптом `bin/homework1`
(в Windows — `bin/homework1.bat`).

## Работа с приложением

Меню позволяет принять транспорт, добавить вещь, вывести отчёт, список
транспорта для новичков и весь инвентарь. Команда `0` завершает программу.
Для транспорта задаются тип, номер, название, простота управления (1–10),
результат проверки исправности (`да`/`нет`) и расход энергии для электрических моделей.
Дробный расход можно вводить через точку или запятую.

Это учебная модель техосмотра: оператор вводит факт исправности,
а `BasicServiceCenter` принимает решение по этому признаку. Отрицательный результат
не добавляет транспорт в парк. При необходимости вместо него через DI подключается
сервис с более сложными проверками.

Демонстрация показывает:

1. Пустой парк и нулевой отчёт.
2. Приёмку самоката (простота 6, расход 2.5), велосипеда (простота 5)
   и электровелосипеда (простота 8, расход 1.5).
3. Отказ в приёмке неисправного самоката: он не появляется в отчётах.
4. Постановку на баланс шлема и зарядной станции (расход 3).
5. Отказ при повторном инвентарном номере.
6. Итог: **3 транспортных средства, 2 вещи, 5 объектов, 7 кВт·ч в сутки**.
7. Список для новичков: самокат и электровелосипед; затем весь инвентарь.

Ошибочный ввод не завершает приложение и не меняет парк. Проверяются пустые
номера и названия, диапазон простоты, неотрицательность и конечность расхода
(в том числе запрещены NaN и бесконечность). Конец ввода корректно завершает меню.
Номера уникальны **среди транспорта и вещей вместе**, с учётом регистра;
пробелы по краям номера и названия удаляются. После отказа техосмотра номер свободен.

## Модель и архитектура

Исходники находятся в [src/main/java/ru/hse/vyshkat](src/main/java/ru/hse/vyshkat).

| Тип / пакет | Ответственность |
| --- | --- |
| `model.InventoryItem` | Контракт названия и инвентарного номера |
| `model.EnergyConsumer` | Контракт суточного расхода энергии, кВт·ч |
| `model.Asset` | Общие неизменяемые данные и их проверка |
| `model.Transport` | Простота управления и факт исправности транспорта |
| `ElectricScooter`, `Bicycle`, `ElectricBicycle` | Виды транспорта |
| `model.Thing`, `Helmet`, `ChargingStation` | Небольшая иерархия вещей |
| `service.ServiceCenter` | Заменяемый контракт техосмотра |
| `service.BasicServiceCenter` | Решение по исправности |
| `service.FleetService` | Приёмка, уникальность номеров, учёт и отчёты |
| `config.AppConfig` | Сборка зависимостей через Spring DI |
| `console.ConsoleApp` | Ввод, вывод и демонстрация |
| `Main` | Создание и закрытие контекста, выбор режима |

Обычный велосипед и шлем не реализуют `EnergyConsumer`: им не требуется
фиктивный метод расхода. Зарядная станция реализует этот интерфейс, поэтому её
энергия тоже входит в общий отчёт. В рамках модели расходы объектов независимы:
показатель станции — её собственный расход, без повторного учёта энергии транспорта.
Число транспорта показывается отдельно от числа вещей и общего числа объектов.

`FleetService` использует одну `LinkedHashMap`, чтобы контролировать уникальность
номеров во всём инвентаре и сохранять порядок добавления. Наружу возвращаются
неизменяемые снимки списков. Учёт однопоточный; отдельный репозиторий и транзакции
для текущего объёма не нужны. Для энергии используется `double`, подходящий для
этого учебного отчёта; в выводе два знака после запятой.

## SOLID и обязательные вопросы

**S — Single Responsibility.** Данные и инварианты находятся в `model`,
решение техосмотра — в `BasicServiceCenter`, учёт — в `FleetService`,
консольный ввод и вывод — в `ConsoleApp`, связывание зависимостей — в `AppConfig`.

**O — Open/Closed.** Новый вид транспорта наследует `Transport`, при необходимости
реализует `EnergyConsumer`. Приёмка, отчёты и подбор новичкам работают без правки
`FleetService`. Это проверяет тест `newTransportTypeWorksWithoutChangingFleetService`.

**L — Liskov Substitution.** Все виды транспорта удовлетворяют общим инвариантам:
непустые номер и название, простота 1–10. Сервис принимает любой `Transport`
и не требует конкретный класс. Неэлектрический велосипед не вынужден выбрасывать
исключение из ненужного метода энергопотребления.

**I — Interface Segregation.** `InventoryItem` и `EnergyConsumer` разделены:
инвентаризируемость не означает потребление электричества. Техосмотр имеет один
метод `approve` и не содержит методов хранения или печати.

**D — Dependency Inversion — наиболее явный принцип.** `FleetService` зависит
от интерфейса `ServiceCenter`, полученного в конструкторе. Он не создаёт
`BasicServiceCenter`. Spring-контейнер создаёт бины из `AppConfig` и внедряет
нужную реализацию по типу. Это настоящий DI-контейнер, а не только ручной `new`.

**Какой принцип ограничен?** OCP сознательно ограничен на границе консоли:
`ConsoleApp.addTransport()` содержит `switch` типов. Новый вид потребует добавить
пункт меню и создание объекта. Для трёх видов это проще реестра фабрик и плагинов;
доменный сервис при этом не меняется. Также `FleetService` объединяет хранение
в памяти и отчёты для одной небольшой задачи учёта: отдельный слой репозиториев
пока не даёт пользы.

**Что произойдёт при расширении?**

- Новый транспорт: добавится класс и пункт меню, основной сервис остаётся прежним.
- Сотрудник: отдельная сущность, не наследующая `Asset` и не реализующая
  `InventoryItem`, поскольку сотрудники не ставятся на баланс. Нужный кадровый
  сервис создаётся отдельно, существующий учёт не ломается.
- Склад запчастей: инвентаризируемые единичные вещи можно добавить как подкласс
  `Thing`. Для остатков по количеству нужен отдельный складской сервис,
  поскольку партия деталей — другая модель, чем один объект с уникальным номером.
- Новый техосмотр: реализация `ServiceCenter` и замена бина в `AppConfig`.
- Новое правило для новичков: сейчас порог 6 задан в `FleetService`. При появлении
  нескольких правил его можно выделить в отдельную политику; заранее она не нужна.

**Какие тесты фиксируют правила и как подменяется зависимость?**

- `FleetServiceTest.inspectionHappensBeforeAcceptanceAndRejectionDoesNotReserveNumber`:
  fake техосмотра сначала отказывает, затем принимает; проверяются вызовы и состояние.
- `FleetServiceTest.beginnerRuleUsesInclusiveThreshold`: параметризованный тест
  значений 1, 5, 6 и 10, включая обе стороны границы.
- `DependencyInjectionTest.primaryStubReplacesInspectionThroughContainer`:
  в реальный Spring-контекст добавлен primary-бин `ServiceCenter`, всегда
  отказывающий. Контейнер внедряет его в production-бин `FleetService`.
- `DependencyInjectionTest.productionContainerWiresActualInspection`:
  штатный контейнер принимает исправный транспорт и отклоняет неисправный.
- `ModelTest`: проверки инвариантов объектов.
- `ConsoleAppTest`: демонстрация, ввод всех типов, ошибочный ввод и конец потока.

Отчёты после сборки:

- Тесты: `build/reports/tests/test/index.html`.
- JaCoCo: `build/reports/jacoco/test/html/index.html`.
- Checkstyle: `build/reports/checkstyle/main.html` и `test.html`.

Порог покрытия проверяется задачей `check` и относится **ко всему модулю**,
включая консоль и точку входа; исключений классов из отчёта нет.
